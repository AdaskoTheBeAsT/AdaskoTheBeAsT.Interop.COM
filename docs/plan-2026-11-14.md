# Library Improvement Plan — Multi-Worker Isolation & Nano Server COM Parity (2026-11-14)

## Review update (2026-11-15)

The seven work items below remain the active scope. These corrections are based
on the current code and the consuming application's vendor docs and skills:

- Keep existing API behavior by default. New unloading and registry-writing
  behavior is explicit opt-in. Adding abstract members to `IComExecutor` would
  break third-party implementations on legacy TFMs; expose a derived capability
  interface and/or extensions while keeping the original interface usable.
- **COM-01/03:** module leases must handle overlapping/nested scopes, concurrent
  loads of the same path, activation rollback and double disposal. Release all
  owned RCWs before reversing factory registrations; keep modules mapped while
  `DllCanUnloadNow` reports live native objects. Never free a shared module just
  because one worker ended. Test immediate directory deletion only after the
  final native reference is actually gone. Wrong-thread/non-LIFO disposal must
  fail without losing the state needed for a correct owner-thread retry.
- **COM-02:** do not silently turn an existing MTA into an STA. Propagate
  `RPC_E_CHANGED_MODE` and balance only initialization references acquired by
  this library, on the same thread.
- **COM-04:** normalize manifests before activation; reject duplicate/conflicting
  CLSIDs, unsafe paths and malformed GUIDs before touching modules or registry.
  Distinguish a known proxy/stub class from a non-creatable VB6 coclass. An
  unavailable ordinary coclass remains a hard failure; never blanket-ignore
  `CLASS_E_CLASSNOTAVAILABLE`. Registry-free activation remains the default.
  Optional HKCU ProgID/TypeLib registration must preserve previous values,
  reference-count overlapping scopes, and roll back only values still owned by
  the scope. Never copy manifest licensee descriptions to logs or diagnostics.
- **COM-05:** an IUnknown vtable may belong to a shared VB6 runtime, tear-off
  interface or proxy, not the vendor DLL. Report this as inconclusive rather
  than claiming that vtable ownership proves server isolation. Allow callers to
  inspect a specific direct native interface and test an actual mismatch.
- **COM-06:** validate rank, element size/type, overflow and bounds; pair every
  `SafeArrayAccessData` with `SafeArrayUnaccessData`. Borrowed arrays are never
  destroyed or modified. BSTR/VARIANT arrays need ownership-aware conversion,
  not the unmanaged numeric-copy path. Cover negative lower bounds and failures.
- **COM-07:** select one native provider by a capability query, not a version
  string. Prefer the Nano implementation and do not duplicate unsafe generated
  machine code or managed teardown callbacks. An older-image compatibility
  provider is opt-in and must use native static lifetime and W^X protection.
- **COM-08 (P0), process startup ordering:** provide/document an idempotent
  startup-thread preparation entry point before concurrent STA workers start.
  Avoid repeated forwarder initialization under contended managed locks on
  partially initialized STA threads. Preserve the existing four-mode provider
  tests, each provider transition in a fresh process.

Validation must include real native COM fixtures on x86/x64, all retained TFMs,
cross-order multi-coclass calls, session recycling and temp-directory cleanup.
SAFEARRAY producer bugs, vendor apartment scratch offsets and binary-specific
finalization patches remain in the application. No image/package publication or
consumer package upgrade is part of this work.

## Executive summary

`AdaskoTheBeAsT.Interop.COM` `v4.2.0` (`Executor`, `ComExecutor`, `ComObjectHandle<T>`, `NanoServerStaShim`, `NanoServerOptions`, and `ActivationContextApi`) works out-of-the-box for single-instance registration-free COM activation. However, four complex multi-worker STA production integrations still had to bypass `Executor` and write custom activation bridges due to **six concrete limitations** in `ActivationContextApi` and `Executor`:

1. **Unbounded static `LoadedModules` cache prevents module unloading and per-worker temp-directory cleanup:** `ActivationContextApi.LoadLibrary` (`ActivationContextApi.cs:114-135`) stores every `LoadLibraryEx` handle in `static ConcurrentDictionary<string, IntPtr> LoadedModules` and never calls `FreeLibrary` or `CoFreeUnusedLibrariesEx`, keeping per-worker isolated DLL copies (`worker_01/server.dll`) locked on disk when sessions recycle or dispose.
2. **Apartment mismatch on uninitialized threads in `RegisterFactoryWithRetry`:** `ActivationContextApi.RegisterFactoryWithRetry` (`ActivationContextApi.cs:601-621`) unconditionally calls `CoInitializeEx(IntPtr.Zero, COINIT_MULTITHREADED)` on `CO_E_NOTINITIALIZED`, even when the manifest `<comClass threadingModel="Apartment" />` requires STA or the current `Thread.CurrentThread.GetApartmentState()` is `ApartmentState.STA`.
3. **Incomplete manifest element support in Nano Server fallback (`<typelib>`, `progid`, proxy/stub graceful skip):** `ActivationContextApi.ReadManifestNodes` (`ActivationContextApi.cs:241-379`) parses only `<comClass clsid="...">`. It ignores `progid` attributes (breaking `CLSIDFromProgID` / `CreateObject` inside VB6, Delphi, and MSXML/ADO components), ignores `<typelib tlbid="...">` (`LoadTypeLibEx`), and fails activation (`CLASS_E_CLASSNOTAVAILABLE`) if a manifest lists a `PSFactoryBuffer` `<comClass>` whose DLL returns `CLASS_E_CLASSNOTAVAILABLE` for proxy/stub CLSIDs when dual/IDispatch marshaling is used instead.
4. **No first-class multi-coclass activation scope (`IComActivationScope`):** `Executor.Create<T>` wraps exactly one root RCW in `ComObjectHandle<T>`. Stateful COM sessions that instantiate multiple peer coclasses per STA worker (`IDatabase`, `ISelector`, `ICurve`, `ISpectrum`) or create/release transient COM objects on every request need a long-lived per-STA-worker activation scope without wrapping a single RCW.
5. **No built-in module-isolation verification helper:** Multi-worker hosting of non-thread-safe STA COM DLLs (writable `.data`/`.bss` sections) relies on each STA worker binding to its own private DLL copy rather than silently resolving a `CLSID` from `HKLM`/`HKCR` on developer machines where the vendor installer was previously registered.
6. **Duplicated Nano Server COM helpers across consumers (SafeArray marshaling, legacy `ole32` IAT shims, `CLSID_DispenserManager`):** Multiple consumers had to duplicate low-level helpers for malformed Delphi `SAFEARRAY` descriptors (missing `FADF_HAVEVARTYPE`), VB6 1-based `SAFEARRAY` bounds, Nano Server `forwarders\ole32.dll` IAT shims, and native `CLSID_DispenserManager` registration for OLE DB / Jet 4.0.

## Detailed technical plan

### COM-01 (P0): Replace unbounded `LoadedModules` leakage with reference-counted module lifetimes

#### Evidence
In `src/AdaskoTheBeAsT.Interop.COM/ActivationContextApi.cs` (`lines 25, 114-135`):
```csharp
private static readonly ConcurrentDictionary<string, IntPtr> LoadedModules = new(StringComparer.OrdinalIgnoreCase);
```
Every fallback `LoadLibrary(dllPath)` call caches the `HMODULE` forever and never calls `FreeLibrary`. When a multi-worker pool (`MaxOperationsPerSession` or pool shutdown) disposes a worker session and deletes its temporary isolated worker directory (`%TEMP%\vendor\worker_01\`), Windows rejects `Directory.Delete` with `UnauthorizedAccessException` / `IOException` because `LoadedModules` still holds an open module reference. Additionally, `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS` (`0x00001100`) should be preferred before `LOAD_WITH_ALTERED_SEARCH_PATH` (`0x00000008`).

#### Design
1. Replace raw `IntPtr` entries in `LoadedModules` with a ref-counted `LoadedModuleEntry` tracking active `FallbackActivation` leases per normalized full path.
2. Add `ComActivationOptions` (defaulting to current keep-loaded behavior if `UnloadModulesOnDeactivate = false`, or opt-in `UnloadModulesOnDeactivate = true` for isolated per-worker copies):
   - When `UnloadModulesOnDeactivate = true` and the last activation referencing `fullPath` deactivates (`DeactivateFallbackContext`), call `CoRevokeClassObject`, `Marshal.Release(classFactory)`, `CoFreeUnusedLibrariesEx(0, 0)`, and `FreeLibrary(moduleHandle)`, removing the entry from `LoadedModules`.
3. Update `LoadLibrary` search order to try `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS` (`0x00001100`) first, then `LOAD_WITH_ALTERED_SEARCH_PATH` (`0x00000008`), then `0`.

#### Acceptance
- Unit and integration tests verify that activating and disposing a per-worker copied COM DLL with `UnloadModulesOnDeactivate = true` unloads the module (`GetModuleHandleW(workerDllPath) == IntPtr.Zero`) and allows immediate `Directory.Delete(workerDir, recursive: true)`.

### COM-02 (P0): Respect `ApartmentState.STA` and manifest `threadingModel` during class-factory registration

#### Evidence
In `src/AdaskoTheBeAsT.Interop.COM/ActivationContextApi.cs` (`lines 151-152, 601-621`):
```csharp
internal virtual int InitializeMultithreadedApartment()
    => NativeMethods.CoInitializeEx(IntPtr.Zero, NativeMethods.COINIT_MULTITHREADED);
```
If a caller creates a `new Thread(...)` and calls `thread.SetApartmentState(ApartmentState.STA)` (or uses a custom thread runner before first P/Invoke initializes OLE) and `CoRegisterClassObject` returns `CO_E_NOTINITIALIZED`, `RegisterFactoryWithRetry` initializes **MTA** (`COINIT_MULTITHREADED`) instead of **STA** (`COINIT_APARTMENTTHREADED`), violating STA affinity for `threadingModel="Apartment"` VB6/Delphi coclasses!

#### Design
1. Capture `threadingModel` from `<comClass threadingModel="..." />` during `TryAddComClassRegistration`.
2. In `RegisterFactoryWithRetry`:
   - Inspect `Thread.CurrentThread.GetApartmentState()` and `registration.ThreadingModel`.
   - Choose `COINIT_APARTMENTTHREADED` (`0x2`) whenever `Thread.CurrentThread.GetApartmentState() == ApartmentState.STA` or `threadingModel` is `"Apartment"` / `"Single"`, falling back to `COINIT_MULTITHREADED` (`0x0`) only for `"Free"` / `"Both"` on non-STA threads.
   - Track whether `ActivationContextApi` performed the `CoInitializeEx` on the thread so `DeactivateFallbackContext` balances `CoUninitialize()` cleanly without uninitializing caller-owned apartments.

#### Acceptance
- Tests cover `CO_E_NOTINITIALIZED` recovery on both `ApartmentState.STA` and `ApartmentState.MTA` threads and verify balanced `CoUninitialize` on scope exit.

### COM-03 (P0): First-class `IComActivationScope` (`Executor.Activate` / `IComExecutor.Activate`)

#### Evidence
`Executor.Create<T>` (`Executor.cs:295-403`) ties activation-context lifetime to a single `ComObjectHandle<T>`. Many real-world STA COM libraries expose a session graph of 5–25 coclasses (`Database`, `Selector`, `Fan`, `Drive`, `Curve`, `Spectrum`, `XmlDocument`) where a long-lived STA worker activates the manifest **once** when the worker starts, creates and releases dozens of transient COM objects across thousands of requests, and deactivates the manifest when the worker shuts down or recycles.

#### Design
Add an explicit, allocation-light scope API to `Executor` and `IComExecutor`:

```csharp
public interface IComActivationScope : IDisposable
{
    bool IsUsingNanoServerFallback { get; }

    IReadOnlyList<IntPtr> LoadedModuleHandles { get; }

    ComExecutionResult PumpPendingMessages(int maxBatch = 64);
}
```

With overloads on `Executor` and `IComExecutor`:
```csharp
public static ComCreateResult<IComActivationScope> Activate(
    string assemblyPath,
    string manifestPath,
    ComActivationOptions? options = null);

public static ComCreateResult<IComActivationScope> Activate(
    ICollection<ComPathDescriptor> descriptors,
    ComActivationOptions? options = null);
```

- On Desktop Windows, `Activate` creates and activates the WinSxS `ACTCTX` stack (`CreateActCtxW` + `ActivateActCtx`) on the calling thread and optionally preloads isolated DLLs when `ComActivationOptions.PreloadModules = true`.
- On Nano Server, `Activate` parses the manifest(s) and registers all class factories on the calling thread via `ActivationContextApi`, keeping them active until `IComActivationScope.Dispose()` unwinds cookies/registrations in reverse order.
- Internally refactor `Executor.Create<T>` to compose over the same core activation state so activation/cleanup logic exists in one place.

#### Acceptance
- Multiple distinct coclasses from single-DLL and multi-DLL manifests can be instantiated via `Activator.CreateInstance(Type.GetTypeFromCLSID(clsid))` / RCW `new` inside a single `IComActivationScope` across repeated calculations on both Desktop Windows and Nano Server, with strict LIFO cookie validation on `Dispose()`.

### COM-04 (P1): Manifest `progid`, `<typelib>`, and `PSFactoryBuffer` support on Nano Server

#### Evidence
In `ActivationContextApi.cs` (`lines 310-379`), `ProcessElement` handles `<file>`, `<dependentAssembly>`, and `<comClass clsid="...">`, leaving three real-world gaps on Nano Server:
1. **`progid` attribute and `<comClass><progid>...</progid></comClass>` child elements:** Legacy COM libraries call `CLSIDFromProgID` (e.g., `MSXML2.DOMDocument.4.0`, `ADODB.Recordset`, or internal VB6 `CreateObject("Lib.Class")`), which fails with `CO_E_CLASSSTRING` (`0x800401F3`) on Nano Server unless `HKCU\Software\Classes\<ProgId>\CLSID` is populated.
2. **`<typelib tlbid="..." version="..." helpdir="..." />`:** Automation / `IDispatch` / dual-interface servers call `LoadRegTypeLib` or rely on type-library registration for marshaling and `ITypeInfo`.
3. **Proxy/stub `<comClass>` entries (`PSFactoryBuffer`):** Manifests generated for ATL/MIDL DLLs often include the proxy/stub CLSID alongside coclasses; when `DllGetClassObject` returns `CLASS_E_CLASSNOTAVAILABLE` for an unused proxy/stub entry, `ActivateFallbackContext` currently aborts the entire manifest (`ActivationContextApi.cs:524-531`).

#### Design
1. Parse optional `progid`, `tlbid`, and `description` metadata on `<comClass>`, child `<progid>` elements, and `<typelib>` elements under `<file>`.
2. When `ComActivationOptions.RegisterCurrentUserProgIdsOnFallback` (default `true` on Nano Server) is enabled, idempotently register `HKCU\Software\Classes\<ProgId>\CLSID` (and clean up or reference-count optional ephemeral ProgIDs if requested).
3. When `<typelib>` is present and `ComActivationOptions.LoadTypeLibsOnFallback` (default `true`) is enabled, call `oleaut32!LoadTypeLibEx(dllPath, REGKIND_NONE, out var typeLib)` (and optional `RegisterTypeLibForUser` under `HKCU` when `RegisterCurrentUserTypeLibsOnFallback = true`).
4. Treat `<comInterfaceProxyStub>` / `PSFactoryBuffer` `CLASS_E_CLASSNOTAVAILABLE` gracefully when controlled by `ComActivationOptions.IgnoreUnavailableProxyStubClasses = true`.

#### Acceptance
- Manifests containing `progid` attributes, child `<progid>` nodes, `<typelib>` nodes, and MIDL `PSFactoryBuffer` entries activate cleanly on Nano Server, and `Type.GetTypeFromProgID` / `CLSIDFromProgID` resolves the manifest CLSID under `ContainerUser`.

### COM-05 (P1): `ComModuleDiagnostics.VerifyInstanceModule` isolation guard

#### Evidence
When a developer workstation has a vendor COM server globally registered in `HKLM\Software\Classes\CLSID` (e.g., pointing to `C:\Program Files (x86)\...`), a subtle manifest path typo or missing coclass entry causes `CoCreateInstance` on Desktop Windows to silently fall back to the globally registered singleton DLL instead of the worker's isolated DLL copy (`worker_01\server.dll`), corrupting mutable `.data`/`.bss` state under parallel load!

#### Design
Add a public diagnostic/assertion utility `ComModuleDiagnostics`:
```csharp
public static class ComModuleDiagnostics
{
    public static IntPtr GetInstanceModuleHandle(object comObject);

    public static void VerifyInstanceModule(object comObject, IntPtr expectedModuleHandle, string? expectedDllPath = null);
}
```
Implemented by querying `Marshal.GetIUnknownForObject(comObject)` (released in `finally`), reading vtable slot 0 (`QueryInterface` function pointer), and resolving the owning `HMODULE` via `GetModuleHandleExW(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS | GET_MODULE_HANDLE_EX_FLAG_UNCHANGED_REFCOUNT, fnPtr, out var hMod)`. Note: when CLR wraps an interface via a proxy/stub across apartments, slot 0 belongs to `combase.dll`/`oleaut32.dll`; detect in-apartment direct vtables vs proxy stubs and report clear diagnostic messages.

#### Acceptance
- Unit tests verify exact `HMODULE` detection on native in-proc COM objects and throw `InvalidOperationException` with hex module addresses and paths when a mismatched `expectedModuleHandle` is supplied.

### COM-06 (P1): `SafeArrayMarshal` utilities for VB6 1-based and Delphi untyped `SAFEARRAY*`

#### Evidence
Two recurring COM marshaling hazards surface across VB6 and Borland Delphi COM servers on .NET:
1. **Delphi `Variants.DynArrayToVariant` / raw `SAFEARRAY*` (`out IntPtr`):** Several Delphi 6/7 COM methods return a borrowed `SAFEARRAY*` lacking `FADF_HAVEVARTYPE (0x0080)` or mismatched `vt` flags, causing the CLR's built-in `[MarshalAs(UnmanagedType.SafeArray)]` marshaler to throw `SafeArrayTypeMismatchException` (`0x80131533`).
2. **VB6 non-zero lower-bound `SAFEARRAY` (`1..N`):** VB6 `Option Base 1` or `Dim arr(1 To N)` returns `System.Array` instances (`float[*]`, `string[*]`, `object[*]`) whose runtime type is not `T[]` (`SZArray`), causing `(double[])variantValue` casts in C# to throw `InvalidCastException`.

#### Design
Add `SafeArrayMarshal` to `AdaskoTheBeAsT.Interop.COM`:
- `T[] CopyFrom borrowedSafeArrayPointer<T>(IntPtr safeArrayPtr, bool destroyAfterRead = false) where T : unmanaged` using `SafeArrayGetDim`, `SafeArrayGetLBound`, `SafeArrayGetUBound`, `SafeArrayGetElemsize`, and `SafeArrayAccessData` / `SafeArrayUnaccessData` (with size validation against `sizeof(T)`).
- `T[] NormalizeVariantArray<T>(object? comArray)` handling `T[]` fast-path zero-copy, 1-based single-dimensional `Array` via `Array.GetLowerBound(0)` / `Array.Copy`, and `VT_VARIANT` element conversion.
- `Array CreateOneBasedArray<T>(ReadOnlySpan<T> items)` (`Array.CreateInstance(typeof(T), [items.Length], [1])`) for VB6 `ByRef` array inputs.

#### Acceptance
- Deterministic unit tests covering `0`-based, `1`-based, negative-lower-bound, empty, borrowed-pointer, and owned-pointer `SAFEARRAY` structures across `float`, `double`, `int`, `short`, and `BSTR`.

### COM-07 (P2): Opt-in Nano Server Legacy OLE2 IAT & `CLSID_DispenserManager` Fallback

#### Evidence
On Nano Server images prior to `1.8.0` (including published `v1.7.0`), `SysWOW64\ole32.dll` delay-load stubs for `OleRun`, `OleSaveToStream`, `OleLoadFromStream`, `CoInitialize`, `OleInitialize`, and `OleUninitialize` fail unless patched in the caller's IAT, and `CLSID_DispenserManager` (`comsvcs.dll`) is absent for MDAC/Jet 4.0 callers.

#### Design
- Expose `NanoServerOptions.EnableLegacyOle2Shim` and `NanoServerOptions.EnableDispenserManagerFallback` (auto-detecting whether OS `nanoserver_sta_shim.dll` `>= 1.8.0` already provides them, and only activating the in-process W^X native stub fallback on older Nano Server images such as `v1.5.0`–`v1.7.0`).
- Ensure the `CLSID_DispenserManager` vtable stub is emitted in pure W^X native code (`PAGE_READWRITE` -> `PAGE_EXECUTE_READ`, never `PAGE_EXECUTE_READWRITE`) so background native OLE DB / Jet threads detaching during `DLL_THREAD_DETACH` after CLR shutdown never re-enter managed code.
- Also update `NanoServerStaShim.cs` (`line 21`) to eliminate `PageExecuteReadWrite = 0x40` in favor of temporary `PAGE_READWRITE` during IAT slot updates followed by restoring original page protection (`VirtualProtect`), aligning with strict W^X security hygiene.

#### Acceptance
- Zero `PAGE_EXECUTE_READWRITE` allocations or VirtualProtect calls remain in `AdaskoTheBeAsT.Interop.COM`, and legacy OLE2 + `CLSID_DispenserManager` tests pass on Nano Server `v1.7.0` and `v1.8.0`.
